# Deploying the backend on Render (primary host)

Branch `server`, deploy root `server/`, Blueprint `server/render.yaml`. This guide contains no credentials: secrets are generated by Render or typed
in Render's dashboard. Render is the deployment target because it runs the **complete** backend, including the Socket.IO server (chat, live announcements,
support and map pushes). Vercel is not a target: its serverless functions cannot host this Socket.IO server. (A REST-only Vercel experiment exists only as
local, uncommitted files and is not part of this branch.)

**Status: prepared and checked locally; NOT deployed.** No Render resource has been created and no Render service URL exists yet. Section 8 lists exactly what was and was not verified.

## 1. What gets created, and where

| Resource | Name | Plan in `render.yaml` | Region | Notes |
|---|---|---|---|---|
| Web service (Node) | `emh-server` | `free` | **Frankfurt** | one long-running instance; Express + Socket.IO on `$PORT` |
| PostgreSQL | `emh-db` | `free` | **Frankfurt** | internal connection string injected as `DATABASE_URL` |

**Region: Frankfurt, Germany. The service and the database must both be in Frankfurt.** Render currently offers five regions (Oregon, Ohio, Virginia, Frankfurt, Singapore) and
**has no London or UK region**, so this deployment is **not hosted in London**; Frankfurt is the nearest listed region to the UK. Each Render region has its own private network, so the web service reaches the
database over the internal URL only if both are in the same region, and a region **cannot be changed after creation** (changing it later means creating new resources and migrating the data). The region list
is Render's current offering and can change, check `https://render.com/docs/regions`.

## 2. Cost and plan implications (checked against Render's docs on 2026-11-09; re-check the pricing page before you rely on it)

Both resources use the `free` plan so that applying the Blueprint does **not** create anything billable. Render itself says free instances should not be used for production.

| | Free web service | Free PostgreSQL |
|---|---|---|
| Idle | **spins down after 15 min without inbound traffic**; waking takes about a minute. HTTP requests and WebSocket messages on an existing connection both count as traffic | - |
| Lifetime | 750 free instance-hours per workspace per month (shared across free web services; suspended when used up) | **expires 30 days after creation**, then a 14-day grace period, then the database and its data are **deleted** unless upgraded |
| Limits | exactly one instance, no scaling out, no shell/SSH, no one-off jobs, no persistent disk, **no pre-deploy command** | one per workspace, 1 GB, **no backups**, no managed pooling |

Consequences for this app:
- Upgrade the database to a paid plan **before day 30** if the data matters (change `plan:` in `server/render.yaml` and sync, or change it in the dashboard).
- The Android client times out after 10 s (connect) / 20 s (read) (`ApiClient.kt`), shorter than a ~1-minute wake-up. After idle, the first request from the app can fail while the service wakes. A paid web plan avoids it; an external monitor hitting `/ping` every ~10 minutes keeps a free instance awake (within the monthly hours).
- Paid plan identifiers in the current Blueprint spec look like `0.5c-512mb`, `1c-2g` (web) and `0.1c-256mb`, `0.5c-1g` (database); prices change, so read Render's pricing page. **Nothing paid was created and none is configured here.**

## 3. What the Blueprint sets and why

| Setting | Value | Reason |
|---|---|---|
| `rootDir` | `server` | build and start run inside `server/`; files outside it are not available to the service (nothing outside is needed) |
| `buildCommand` | `npm ci --omit=dev` | reproducible install from `package-lock.json`, production dependencies only (the dev-only embedded PostgreSQL is not installed) |
| `startCommand` | `npm start` | `node src/server.js`: the full server with Socket.IO |
| `healthCheckPath` | `/ping` | unauthenticated, outside the API rate limiter, runs a database query. Render treats 2xx/3xx as healthy and requires an answer within 5 s |
| `NODE_ENV` | `production` | enables `trust proxy` (real client IPs behind Render's proxy), strict CORS and the 32-character JWT secret rule |
| `DATABASE_URL` | `fromDatabase: emh-db, connectionString` | internal URL, injected by Render; never typed or committed |
| `JWT_SECRET` | `generateValue: true` | Render generates a random 256-bit value (well over the 32 characters production requires); not in Git |
| `MIGRATE_ON_BOOT` | `"false"` | see section 4 |
| Node version | from `engines.node` `>=20.19.0 <25` | Render resolves a bounded range to the newest matching 24.x (an unbounded range would pick the newest major) |
| Region | `frankfurt` for both | no London/UK region exists on Render; the internal database URL only works inside the same region; a region cannot be changed after creation, so settle it before the first apply |

## 4. Migrations and seeding: never on a restart

The server used to migrate on every boot and seed an empty database automatically. For production that is now off (development and tests are unchanged):

| Behaviour | Development / tests | Production (`NODE_ENV=production`) |
|---|---|---|
| Apply migrations at boot | yes | **no**, unless you set `MIGRATE_ON_BOOT=true` |
| Pending migrations found at boot | applied | **server refuses to start** and names them, so a forgotten migration fails the deploy and the previous version keeps running |
| Seed an empty database at boot | yes | **no** (`SEED_ON_BOOT=true` is an explicit opt-in that forces the idempotent seed; do not set it) |
| Demo account | created | not created unless `SEED_DEMO_USER=true` + `DEMO_USER_PASSWORD` |

Render's Pre-Deploy Command would be the natural place to migrate, but it is **only available on paid web services**, so it is not configured. (On a paid plan you could add
`preDeployCommand: npm run db:migrate` to the service; that runs once per deploy, not per restart. It is your call and it is not enabled.) Instead, migrations and the one-time seed are run
deliberately from your machine against the database's **external** URL, as in step 3 below.

## 5. Environment variables

| Variable | Set by | Notes |
|---|---|---|
| `NODE_ENV` | Blueprint | `production` |
| `DATABASE_URL` | Blueprint (from `emh-db`) | internal connection string. On the internal network TLS is optional and uses self-signed certificates, so do **not** add `sslmode=verify-*` |
| `JWT_SECRET` | Blueprint (generated) | stays stable across deploys; rotating it signs everyone out |
| `MIGRATE_ON_BOOT` | Blueprint | `false` |

| `CORS_ORIGINS` | you, in the dashboard, only if a browser front end calls the API | comma-separated exact origins. Empty in production = no browser access (the Android app sends no Origin header and is unaffected). Socket.IO uses the same allowlist |
| `JWT_EXPIRES_IN`, `BCRYPT_ROUNDS` | optional | defaults `7d`, `10` |
| `SEED_DEMO_USER`, `DEMO_USER_PASSWORD`, `SEED_ON_BOOT` | leave unset | see section 4 |
| `API_BASE_URL`, `USE_EMBEDDED_PG`, `EMBEDDED_PG_*` | not used on Render | |

## 6. Steps

1. **Connect the repository to Render** (GitHub) and make sure the branch you deploy (`server`) is on GitHub.
2. **Create the Blueprint.** Render dashboard -> New -> Blueprint -> pick the repository -> branch `server` -> **Blueprint Path: `server/render.yaml`** -> review the plan (a web service and a database, both `free`, both **Frankfurt**) -> Deploy Blueprint.
   The first deploy **builds but then fails to start with "migration(s) pending"**. That is the safety check working: the database is empty. Continue with step 3; the failed deploy leaves nothing running.
3. **Migrate and seed once, from your machine.** In the dashboard open `emh-db` -> Info -> copy the **External Database URL** (external access is open to any IP by default but still needs the credentials; external connections are always encrypted).
   ```
   cd server
   npm ci
   # bash
   export DATABASE_URL="<external URL>?sslmode=require"
   export JWT_SECRET="any-throwaway-value-of-32-or-more-characters"   # required to start the config module; not stored or used by migrate/seed
   export NODE_ENV=production                                          # IMPORTANT: keeps the demo account (published password) out of the database
   npm run db:migrate     # applies 001..009 (idempotent; one transaction per file)
   npm run db:seed        # venues, graph edges, sample events and announcements
   ```
   PowerShell: `$env:DATABASE_URL="..."`, `$env:JWT_SECRET="..."`, `$env:NODE_ENV="production"`.
   With the current `pg` client `sslmode=require` verifies the certificate. If you get a certificate error, append `&uselibpqcompat=true` (encrypts without verifying the certificate) or follow Render's guidance for the external certificate. This step was **not** run against a real Render database.
   Optional afterwards: restrict the database's external access (Networking -> allow list) to your own IP.
4. **Redeploy.** Dashboard -> `emh-server` -> Manual Deploy -> Deploy latest commit. It now starts, passes `/ping`, and goes live. Copy the service URL (`https://<name>.onrender.com`).
5. **Create the first admin.** Registration always creates a `student`, and event creation needs organizer/admin. Register your own account (`POST /api/auth/register`), then promote it once in SQL:
   `UPDATE users SET role = 'admin' WHERE email = '<your email>';` (use `psql` with the external URL, or the dashboard's database tools). After that, manage roles through `/api/manage/users`.
6. **Verify** (replace `<url>`):
   ```
   curl -s https://<url>/ping                       # status ok, database connected, 14 venues, contractVersion 1.6.0
   curl -s https://<url>/api/events                 # seeded events
   curl -s -X POST https://<url>/api/auth/login -H "content-type: application/json" -d '{"email":"x@y.z","password":"wrong"}'   # 401
   ```
   Socket.IO over WebSocket (from `server/` after `npm ci`; use `wss`/`https`):
   `node -e "const {io}=require('socket.io-client');const s=io('https://<url>',{transports:['websocket']});s.on('connect',()=>{console.log('connected',s.id);s.close()});s.on('connect_error',e=>{console.log('ERR',e.message);process.exit(1)})"`
7. **Android.** Section 7.

Later releases that add migration files: run `npm run db:migrate` against the database first (migrations in this project are additive), then deploy. If you deploy first, the new version refuses to start (safe) until you migrate and redeploy.

## 7. Android app: API base URL (development and production)

The app already takes its backend from `BuildConfig.API_BASE_URL` (used by both the REST client and the Socket.IO client). It must be the **server root, without `/api`** (`https://<name>.onrender.com/`).
Configure it per build type (full rules are in the comment block above `android {` in `app/build.gradle.kts`); most specific wins:

| Where | Debug | Release |
|---|---|---|
| Gradle CLI | `-PAPI_BASE_URL_DEBUG=...` | `-PAPI_BASE_URL_RELEASE=...` |
| `local.properties` (untracked, this machine) | `API_BASE_URL_DEBUG=...` | `API_BASE_URL_RELEASE=...` |
| Either, both build types | `-PAPI_BASE_URL=...` / `API_BASE_URL=...` (unchanged legacy key) | same |
| Default | `http://10.0.2.2:3000/` (emulator alias for the local server) | none: a placeholder, and **`assembleRelease`/`bundleRelease` fail** until a real `https://` root is set |

**Where to enter the Render URL once you have it:** in `local.properties` (repo root of the Android project, next to `settings.gradle.kts`; create it if missing, it is git-ignored):
```
API_BASE_URL_RELEASE=https://<your-service>.onrender.com/
```
or on the command line: `./gradlew :app:assembleRelease -PAPI_BASE_URL_RELEASE=https://<your-service>.onrender.com/`. No URL is hard-coded in the repository because none exists yet; the Render URL is only known after the service is created.
To run a debug build against the deployed server instead of a local one: `API_BASE_URL_DEBUG=https://<your-service>.onrender.com/`.
Release builds forbid cleartext traffic (`src/main/res/xml/network_security_config.xml`); the debug config allows it for local development.

## 9. Known limits

- **One instance only.** Socket.IO rooms and the venue registry are in memory; a second instance would not share them (Render assigns each WebSocket to a random instance and the app has no shared adapter). Keep `numInstances` at 1 unless you add a shared store.
- Rate limiting uses per-instance memory (fine for one instance).
- `/ping` runs a database query on every health check (every few seconds), so the database is never idle.
- Deploys and restarts close WebSocket connections (Render sends SIGTERM, 30 s to stop); clients must reconnect. The Socket.IO client does this by default.
- The free database has no backups. Take your own `pg_dump` if the data matters.
