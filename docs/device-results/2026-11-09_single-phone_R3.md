## 4. Local ingest (sender side only)

Event `solo-ev-01`, payload `SOLO-01`, injected with the explicit-component broadcast (attempt 3), phone time 22:15:47.015:
- logcat 22:15:47.029 (14 ms later): `ingest solo-ev-01 (UVF) -> flooding over BLE` (wire id `UVF`).
- Hop counters after: `relayed 0 · delivered 0 · sent 1 · dups 0 · ttl-drops 0 · no-relay drops 0 · max hops 0`, `(no peers in range)` -> `sent` 0 -> 1, nothing else moved.
- Console: one `#UVF "SOLO-01" CTZ -> 0 hops [IN_FLIGHT]` row at 22:15:47.028, then four `[RELAYED]` rows at 22:15:48.485, 49.488, 50.490, 51.493. These are the node **re-sending its own message** during the 5-second rebroadcast window (about 1 s apart), not router relays: the `relayed` counter stayed 0.
- The app stayed up; no errors.

Attempts that did **not** deliver anything to the app (all on the phone, nothing was injected by them):
1. `-e payload "SOLO 01"`: `adb shell` split the space, so `01` became the target package (`pkg=01`).
2. Implicit form with a space-free payload (the form in the plan and in the `IngestReceiver` javadoc): `Broadcast completed: result=0` and the activity manager logged it as enqueued, but the app logged **no `ingest` line**. On this Android 16 phone the implicit broadcast was not delivered to the manifest receiver.
3. Explicit `-n com.epics.bitchat/.mesh.IngestReceiver`: delivered. **Exactly one `ingest` event reached the app.**

**What this does NOT test:** delivery to any other phone, whether a nearby receiver shows or relays the event once, duplicate suppression across two ingesting phones (the ANNOUNCE source-key exception), fanout, the late re-ingest/expiry behaviour, or the fragmented (>14 chars) path. `delivered` and `relayed` staying 0 is expected with no peer and proves nothing about receivers.

## 5. Issues and observations (none blocked the checks)

- **Plan bug fixed in the plan (T4/T1B):** the documented implicit `am broadcast -a ...INGEST` did not reach the receiver on this phone and a space in the payload breaks `adb shell` parsing. Use `-n com.epics.bitchat/.mesh.IngestReceiver` and a payload without spaces (or double-quote it as `"'SOLO 01'"`).
- **Secure Folder user:** plain `adb shell pm list packages com.epics.bitchat` failed with `SecurityException: Shell does not have permission to access user 150`. Passing `--user 0` works. Use `--user 0` on this phone for `pm`/`install`.
- **Git Bash path conversion:** `adb shell uiautomator dump /sdcard/x.xml` and `pull` were first mangled to `C:/Program Files/Git/sdcard/...` (no files lost; nothing was deleted). Set `MSYS_NO_PATHCONV=1` and use Windows-style local paths (`E:/...`) for `adb pull`/`>`.
- **`E/BluetoothLeAdvertiser: Callback not registered or already removed`** at 22:12:07.153, immediately before the advertiser started (`onAdvertisingSetStarted ... 0`). Looks like a stop-before-start of a callback that did not exist yet; no functional effect observed. Not investigated further.
- **Advertising churn:** 74 `Stop AdvertingSet` / restart cycles in ~4.5 min (first at 22:12:17, last 22:16:47), including the 5-second ingest rebroadcast window. Not analysed; no scan stall, no errors. Whether this is by design (per-send advert cycling, ~150 ms blast cadence) is not established here.
- **Other logcat noise** in the app process (`E/QT [QT]file does not exist`, `E/ashmem Pinning is deprecated`) comes from the platform/OEM, not the app's mesh code.
- **Counters cannot be reset** from the UI (restarting the mesh does), as the plan says; the baseline here is a fresh install, so the zeros are real zeros.
- The evidence screenshots include the phone's status bar (installed-app notification icons).
